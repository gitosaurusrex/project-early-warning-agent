# Project Early-Warning Agent (pewa)

Watches a project's Jira, GitHub and Slack activity, flags epics at risk of slipping with
linked evidence, and drafts status updates. It can **replay history** as of any past date
using only the data that existed then, so it can be backtested on finished projects.

See [SPEC.md](SPEC.md) for the full design and [DECISIONS.md](DECISIONS.md) for judgment
calls made while building it.

## Quick start (Atlas demo, no credentials)

Requires [uv](https://docs.astral.sh/uv/) and Python 3.12+.

```bash
uv sync                                   # install
uv run pewa init                          # create pewa.db and .env
uv run pewa ingest --fixtures atlas       # load the synthetic "Atlas" project
uv run pewa snapshot --as-of 2026-02-13   # what was known at end of week 6
uv run pewa snapshot --as-of 2026-03-13   # ...and at the end of the project
uv run pewa assess --as-of 2026-02-13     # rate every epic green/amber/red with cited evidence
uv run pewa report --as-of 2026-02-13     # draft the exec + engineering status updates (Markdown)
uv run pewa backtest --from 2026-01-05 --to 2026-03-13 --step 7d   # replay week by week, score vs outcomes
uv run pewa serve                         # dashboard at http://127.0.0.1:8000
```

Or load the whole demo in one step, including two weekly runs and a backtest, with no model
calls: `uv run pewa demo && uv run pewa serve`.

`pewa assess` and `pewa report` call Claude (model from `PEWA_MODEL`, default `claude-sonnet-5-5`) when
`PEWA_ANTHROPIC_API_KEY` or `ANTHROPIC_API_KEY` is set. Without a key, or with `--dry-run`, it uses an offline heuristic
responder instead (see below), so the demo still runs end to end.

`--as-of` takes a date (meaning the end of that day, UTC) or an ISO datetime. Re-running
`ingest` is safe: events are de-duplicated and only new ones are added.

## The Atlas dataset

`data/fixtures/atlas/` holds a fictional 10-week project (5 Jan to 13 Mar 2026) at Larkspur Labs:
6 engineers, 5 epics, 80 tickets, 69 PRs and 428 Slack messages across three channels.
It is generated by `scripts/make_fixtures.py` (deterministic; a test checks the committed files
are up to date). Four stories are planted:

| Epic | Story | Outcome |
|---|---|---|
| ATL-1 Payments API | Healthy until week 4. Then a PR waits 8 business days for another team's review while Slack shows the owner blocked | slips 2 weeks |
| ATL-2 Search revamp | Scope grows 40% in weeks 5–6 | slips 1 week |
| ATL-3 Onboarding flow | Noisy: heavy design chatter, a reopened ticket, flaky CI, one "waiting on design" | ships on time |
| ATL-4 Notifications, ATL-5 Admin reporting | Healthy controls | ship on time |

Ground truth is in `outcomes.json` and is loaded into the `outcomes` table on ingest.

## How it works

- **Events are append-only** (`events` table), unique on project/source/kind/entity/time, so
  ingestion is idempotent. Each event gets a stable id (`evt_…`) used later as an evidence id.
- **Entity versions** (`entity_versions`) are derived from events: one row per change to a
  ticket, epic or PR, valid from the moment of that change.
- **Snapshots** (`pewa/snapshot.py`) read only events with `occurred_at <= as_of` and the entity
  version valid at `as_of`. Links between Slack/GitHub activity and epics are resolved from that
  past state, so a ticket moved to another epic later doesn't move its old activity.
- **Linking** (`pewa/linking.py`): Jira children by parent; PRs by ticket keys in the title,
  branch or body; Slack by ticket keys or PR URLs, with thread replies inheriting the root's
  links. Unlinked messages are kept but not attributed to an epic.

## Signals and assessment

`pewa assess` runs, for one `as_of` moment: snapshot, then signals, then one LLM call per open
epic, and stores the result as a run (`runs`, `assessments`; every model call is logged to `llm_calls`).

**Signals** (`pewa/signals.py`) are cheap deterministic detectors. Thresholds come from `.env`.

| Signal | Fires when |
|---|---|
| `stale_review` | an open PR has waited more than `PEWA_STALE_REVIEW_DAYS` (3) business days since its latest review request |
| `stale_ticket` | an in-progress ticket has no linked Jira, GitHub or Slack activity for more than `PEWA_STALE_TICKET_DAYS` (5) business days |
| `reopened` | a ticket moved backwards in the workflow within the lookback window (`PEWA_SIGNAL_LOOKBACK_DAYS`, 14) |
| `due_date_pushed` | the due date moved later (count and total days) |
| `scope_growth` | children added after the epic started exceed `PEWA_SCOPE_GROWTH_PCT` (20%) |
| `ci_flaky` | a PR failed CI at least `PEWA_CI_FLAKY_FAILURES` (2) times within the lookback window |
| `burn_gap` | open points can't be finished by the due date at the epic's trailing `PEWA_BURN_WINDOW_WEEKS` (4) week pace |
| `owner_overload` | one assignee has more than `PEWA_OWNER_OVERLOAD_N` (3) tickets in progress across epics |
| `blocker_language` | linked Slack messages within the lookback window use `PEWA_BLOCKER_PHRASES` ("blocked on", "waiting on", ...) |

**Assessment** (`pewa/assess.py`, prompts in `pewa/prompts/`) gives the model the epic, a
child-ticket summary, the signals, and up to 40 events. Each event has an evidence id (signal
evidence first, then recent Slack, then recent activity). The reply must be strict JSON, and
these rules are enforced in code:
- evidence ids not in the input are dropped (and recorded);
- amber and red ratings must keep at least one valid citation;
- an invalid reply is retried once with the validation error; a second failure is stored as
  `rating: "unknown"` with the error.

Done epics are recorded as green without a model call. On models that support it, requests opt
into server-side refusal fallbacks (`fallbacks: "default"`), so a safety-classifier decline is
retried on a fallback model rather than failing.

**Dry-run** (`--dry-run`, or no API key): the model call is replaced by a deterministic
responder that rates from signal severity and cites the signals' evidence. It goes through the
same validation and storage. It is a transparent baseline for demos and tests, not a substitute
for the model.

## Status reports

`pewa report [--as-of DATE] [--variant exec|eng|both] [--out FILE] [--dry-run]` drafts two
Markdown updates from the latest stored run on or before `--as-of`. It never runs an assessment
itself, so run `pewa assess` first.

- **Exec** (≤ 200 words): overall RAG (the worst epic rating), top 3 risks, decisions needed,
  and rating changes since last week.
- **Engineering** (≤ 600 words): one section per epic with owner, due date, rationale, key risks
  linked to their evidence, and next actions.

"Last week" is the newest run at least 6 days older from the same model. Ratings from a
different model or from dry-run are never compared. The model may only restate the
assessments. These checks are enforced in code (`pewa/report.py`):
- the word limit;
- every ticket key, evidence id and URL in the draft must appear in the input;
- the engineering draft must cover every epic.

A failing draft is retried once with the problem. If it fails again, the deterministic template
(`pewa/report_templates/`) is used and the reason is reported. Dry-run uses that template directly.

## Dashboard

`pewa serve [--host 127.0.0.1] [--port 8000] [--dry-run]` starts a local dashboard for
`PEWA_PROJECT`:
- **Overview**: each epic's rating, trend arrow against the previous run, confidence and
  rationale, and feedback counts. A date picker opens the run for a date or runs a new
  assessment for it, and an earlier-runs menu reopens any stored run.
- **Epic detail**: rationale, key risks with evidence links, suggested actions, a timeline of
  the events behind each signal and citation, the epic's rating history, and 👍/👎 feedback
  with an optional note (stored in `feedback`).
- **Reports**: generate either draft for any run and copy the Markdown.

Evidence links open the real Jira/GitHub/Slack page. Fixture URLs (the `.example` domain) open
a local view of the stored event instead. HTMX comes from a CDN for in-place updates. Every form
also works as a plain form post, so the dashboard still works offline. It has no authentication
and binds to localhost by default.

## Backtesting

```bash
uv run pewa backtest --from 2026-01-05 --to 2026-03-13 --step 7d [--model M] [--label L] [--dry-run]
uv run pewa backtests            # list stored backtests with their headline metrics
uv run pewa backtests 3          # re-score backtest 3 and rewrite its reports
uv run pewa compare 2 3          # side by side, e.g. two prompts or two models
```

A backtest assesses the project as of each step date (inclusive of `--from`; the last step is the
last one on or before `--to`). Each assessment sees only the data that existed then. Each step
is stored as an ordinary run (mode `backtest`), so it never shows up in the live overview or in
reports. Without `--from`/`--to`, the backtest spans the project's events.

Metrics, against the `outcomes` table:

| Metric | Meaning |
|---|---|
| Lead time | Planned date minus the first amber/red rating, for slipped epics that were flagged |
| Sustained lead time | Planned date minus the start of the amber/red streak still running at the last step before it (a warning later withdrawn doesn't count) |
| Recall | Slipped epics rated amber/red at some step **before their planned date** |
| Precision | Epics flagged before their planned date that actually slipped |
| False alarm rate | On-time epics that were flagged anyway |
| Citation validity | Cited evidence ids that exist and are linked to that epic as of the step, including made-up ids the validator dropped |

Ratings on or after an epic's planned date don't count as flags: an epic that is still open
on its due date is late by definition. Metrics are recomputed from the stored runs each time, so
feedback added later (from the dashboard) shows up in the report.

Reports go to `backtest_reports/` (change it with `--out`) as Markdown and as a self-contained
HTML page. The HTML page has a rating-strip chart: one row per epic and one cell per step, with
the planned and actual delivery dates marked. The dashboard's **Backtests** page shows the same
chart with clickable cells, the metrics, and a two-backtest comparison.

Model calls and their estimated cost are recorded per backtest. A dry-run backtest is free. A
real one on Atlas makes about 40 calls (done epics are skipped).

## Connecting real sources

Every connector is read-only and only issues GET requests. Tokens are read from environment
variables (or `.env`) and are never logged. Any source whose credentials are missing is skipped
with a warning.

```bash
export PEWA_PROJECT=billing            # a name for your project; must not be "atlas"
uv run pewa ingest                     # all configured sources; re-run any time to sync new activity
uv run pewa ingest --source jira --full   # re-fetch one source's whole history
uv run pewa outcomes --derive          # ground truth from finished epics, for backtests
uv run pewa assess                     # rate every open epic as of now
```

The first sync reads full history. Later syncs start from each source's last ingested event,
and anything already stored is ignored. If one source fails (bad token, missing scope, rate
limit that won't reset soon), the others are still saved. The failure is reported and
`pewa ingest` exits with status 1.

### Jira Cloud

| Variable | Value |
|---|---|
| `JIRA_BASE_URL` | `https://your-site.atlassian.net` |
| `JIRA_EMAIL` | the Atlassian account the token belongs to |
| `JIRA_API_TOKEN` | an API token from [id.atlassian.com](https://id.atlassian.com/manage-profile/security/api-tokens). It acts as that account, so use one that can only *browse* the project |
| `JIRA_PROJECT_KEY` | e.g. `BILL` |
| `JIRA_POINTS_FIELD` | the story-points custom field id (default `customfield_10016`; find yours under Settings → Issues → Custom fields) |
| `JIRA_EPIC_LINK_FIELD` | optional: the classic "Epic Link" field id, for projects that don't use `parent` |
| `JIRA_STATUS_MAP` | optional: `Jira status=pewa status` pairs, e.g. `Code Review=In Review,QA=In Review` |

pewa reads issues with their changelogs (`/rest/api/3/search/jql` with `expand=changelog`, plus
`/rest/api/3/issue/{key}/changelog` for long histories). It replays each issue's status,
assignee, due date, parent, points, title and sprint changes as events. Jira statuses are
mapped onto pewa's four-step workflow (To Do, In Progress, In Review, Done) by their status
category. An in-progress status with "review" in its name counts as In Review, and
`JIRA_STATUS_MAP` overrides either rule.

### GitHub

| Variable | Value |
|---|---|
| `GITHUB_TOKEN` | a [fine-grained token](https://github.com/settings/personal-access-tokens) with read-only **Pull requests**, **Issues** and **Checks** (plus the default **Metadata**) on the repos below |
| `GITHUB_REPOS` | comma-separated `owner/repo` list |
| `GITHUB_API_URL` | optional, for GitHub Enterprise Server (`https://ghe.example.com/api/v3`) |

For each pull request updated since the last sync, pewa reads the PR, its timeline (review
requests, reviews, merge, close, reopen) and the check runs on its last 30 commits (failed or
timed-out runs become `ci_failed`). Ticket keys in a PR's title, branch or body link it to Jira.
GitHub's rate limits are respected: pewa waits for the reset when it is under two minutes away,
and otherwise stops with a clear error.

### Slack

| Variable | Value |
|---|---|
| `SLACK_BOT_TOKEN` | the bot token (`xoxb-…`) of a Slack app with **channels:history**, **channels:read** (and **groups:history**, **groups:read** for private channels) |
| `SLACK_CHANNELS` | comma-separated channel **ids** (`C0123…`; in Slack, open the channel details to copy it) |
| `SLACK_THREAD_LOOKBACK_DAYS` | optional (default 14): how far back incremental syncs re-read threads for new replies |

Invite the bot to each channel (`/invite @your-app`). pewa reads channel history and thread
replies. Messages mentioning a ticket key or PR URL are linked to that epic, and replies inherit
the thread's links. Message text is stored locally (the blocker-language signal and linking need
it) but is never logged. People appear as Slack user ids, since resolving names would need the
extra `users:read` scope.

### Ground truth for backtests

Backtests score ratings against the `outcomes` table. For a live project, either derive it from
finished epics (`pewa outcomes --derive`: planned = the first due date set, delivered = when the
epic reached Done) or load your own JSON in the Atlas format (`pewa outcomes --file
outcomes.json`). `pewa outcomes` lists what's stored.

## Hosting

`render.yaml` is a [Render Blueprint](https://render.com/docs/blueprint-spec) for a hosted,
password-protected copy of the Atlas demo:

1. In Render: **New → Blueprint**, connect this GitHub repo, and pick the `main` branch.
2. When asked for `PEWA_ANTHROPIC_API_KEY`, leave it empty to keep the free offline responder,
   or paste a key so signed-in visitors can run real assessments and reports (billed to it).
3. After the deploy, open the service's **Environment** tab and copy the generated
   `PEWA_DASHBOARD_PASSWORD`. The site asks for it on every page (any username works).

The service runs `pewa demo` (loads Atlas with dry-run assessments for weeks 5–6 and a dry-run
backtest in about 3 seconds, no model calls), then `pewa serve --host 0.0.0.0` on Render's
`PORT`. It uses the free plan, which has no persistent disk and sleeps when idle. The demo is
rebuilt whenever the instance starts, and feedback or runs added from the dashboard are lost
then. To keep them, move to a paid plan and enable the commented-out disk in `render.yaml`.

Anywhere else, the same two commands work. Setting `PEWA_DASHBOARD_PASSWORD` turns on the
password prompt (HTTP Basic auth; serve it over HTTPS). `pewa serve` refuses to listen beyond
localhost without one, unless you pass `--no-auth` because a proxy in front handles sign-in.
`/healthz` stays public for health checks and only reports `{"ok": true}`.

## Development

```bash
uv run pytest                            # all tests (the opt-in `llm` marker is skipped)
PEWA_ANTHROPIC_API_KEY=... uv run pytest -m llm   # real-model check: Epic A flagged a week early
uv run python scripts/make_fixtures.py   # regenerate Atlas after changing the generator
```

Settings come from environment variables or `.env`; see `.env.example`. Sources without
credentials are skipped with a warning. `pewa ingest` without `--fixtures` falls back to the Atlas
fixtures when no source has credentials. Connector tests mock all HTTP with respx, so the suite
never touches a real Jira, GitHub or Slack.
